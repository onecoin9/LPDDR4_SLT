# 邮件写作进阶规范（SKILL）

> 用途：把「一次写完整，再 review」的邮件写作方法固化为可复用标准，确保每封邮件都能回答四个问题：**问题是什么 / 会导致什么后果 / 关键路径在哪 / 谁承担结果**。
> 适用场景：向上汇报、风险升级、跨部门协调、客户同步、回复确认、拒绝承接。
> 双版本：**标准版（默认起草稿）** 与**简洁版（≤ 200 字，由标准版手工删减而成）**，骨架见第四节。
> 🔁 写作流程：**标准版写全 → 自己删减一次 → 用 4.7 六条验收 → 复盘差异**（见 4.6）。
> 存放目录：草稿归档到 `06_杂项/05_邮件/邮件草稿/`，命名 `YYYYMMDD_主题.md`（或 `.html`）。
> 🔑 核心一句话：**邮件不是记事本，是决策请求单。** 收件人读完不回邮件也能做决定，才算写明白。

---

## 一、进阶四阶（判断自己在哪一层）

| 层级 | 特征 | 收件人的反应 |
| --- | --- | --- |
| **L0 流水账** | 只写"我做了什么、在推进中" | "所以呢？要我干嘛？" |
| **L1 结论先行** | 主题行和第一段就给结论/判断 | "知道了，但严重吗？" |
| **L2 后果穿透** | 每个问题都写到具体业务结果（订单 / 交付 / 客户 / 成本） | "这事得管。" |
| **L3 关键路径** | 只锁定唯一真卡点，给出最晚决策时间与不决策的默认结果 | "今天就得定。" |
| **L4 责任闭环** | 责任落到具体人，给 A/B 选项，明确谁承担结果 | 直接回复决策 |

**判定标准：** 收件人能否只读第一段就做出决策。不能，则层级不够。

> 领导反馈的"软件人力评估没法完成 → 影响商务订单引入 → 谁来承担"，本质是要求邮件从 L1 直接写到 L4。

---

## 二、起草顺序：一次写完，再 review

**禁止边写边改。** 边写边改会打断逻辑链，最常见的结果是"问题写了、后果忘了、责任漏了"。

### 2.1 起草阶段（一次成稿，不停笔）

按顺序写完六块，中途不回头润色：

1. **一句话结论**（收件人只需记住这一句）
2. **事实与证据**（时间、数量、数据、出处）
3. **后果**（不解决会怎样，尽量量化）
4. **关键路径**（卡在谁、最晚何时必须决策、不决策的默认结果）
5. **请求**（要谁、何时、做什么；能给选项就给 A/B）
6. **署名 / 附件**

### 2.2 Review 阶段（三遍，每遍只查一件事）

| 遍次 | 只查这个 | 常见漏项 |
| --- | --- | --- |
| **第一遍 查事实** | 数字、日期、人名、范围、责任边界是否准确 | "大概""可能""尽快"等无法执行的词 |
| **第二遍 查逻辑** | 问题 → 后果 → 关键路径 → 请求 是否一条线 | 只描述现象没有结论；后果与问题不匹配 |
| **第三遍 查精简** | 删客套、删背景铺陈、删重复，一段只留一个信息点 | 背景占一半篇幅、结论藏在第三段 |

> Review 时切换到**收件人视角**：假设自己只有 30 秒，只读主题行和第一段，能否知道"要不要管、什么时候管、不管会怎样"。

## 三、四问骨架（领导要的四件事）

### 3.1 问题（What）—— 一句话说到边界

写清"什么事没成 / 什么做不了 / 什么会延误"，必须带**范围、数量、时间**。

- ❌ 软件人力评估还在推进中。
- ✅ 软件人力评估无法在本周内完成：需 3 名具备 XX 平台量产经验的工程师，当前可投入 0 人。

### 3.2 后果（So what）—— 必须落到业务结果

后果优先级：**订单 / 收入 > 客户交付 > 项目节点 > 成本 > 内部效率**。只写"影响进度"等于没写。

- ❌ 会影响项目进度。
- ✅ 人力评估无法出具 → 报价与排期无法确定 → 商务本周无法提交方案 → 客户订单引入推迟至少 2 周（客户 11/05 评审）。

**写法：** 用箭头把因果链串起来，最多三层，每层都必须是可验证的事实，不是猜测。

### 3.3 关键路径（Critical path）—— 只锁一个卡点

不是把所有问题平铺，而是找出**真正卡住整条链的那一个环节**，并给出：

1. 卡点是谁 / 是什么（唯一）
2. 前置依赖是什么（其余条件是否已具备）
3. **最晚决策时间**（由交付节点倒推，不写"尽快"）
4. **不决策的默认结果**（默认延期 / 默认按最保守方案对外承诺）

- ❌ 希望尽快协调资源支持。
- ✅ 唯一卡点是研发对软件人力的确认，其余条件已具备；该确认最晚 10/20 完成，否则 11/05 客户评审无法进行；若 10/20 未确认，默认按"延期 2 周"对外承诺。

### 3.4 责任（Who bears it）—— 落到具体人

写清"谁做、谁决策、谁承担结果"。**禁止使用"相关部门""大家""有关同事"。**

- ❌ 请相关部门支持，谢谢。
- ✅ 请研发张 X 于 10/20 前给出人力结论；若无法给出，请在邮件中确认由研发侧承担订单延期结果，我同步商务调整对外承诺。

**句式：** 责任人 + 动作 + 时间 + 不做的后果。

## 四、双版本：标准版 / 简洁版

所有邮件先选版本，再落笔。两版共用四问，差别只在**展开度**。

### 4.1 选版标准

| 场景 | 版本 | 目标篇幅 |
| --- | --- | --- |
| **所有邮件的第一步** | **标准版（默认起草稿）**：先把四问写全，不漏项 | 300–400 字，正文一屏 |
| 向上决策请求、跨部门升级、需书面留痕追责、对方已拖过一轮 | **标准版**，直接发，不删减 | 300–400 字 |
| 日常催办、平级同步、回复确认、信息收集、对方配合度高 | 标准版写完 → **自己删减**成简洁版 → 过 4.7 验收后发出 | ≤ 200 字，手机一屏 |

> **永远从标准版起步。** 标准版写不全，简洁版一定漏项；只有先写全，删减才是在"取舍"，而不是在"丢信息"。
> 删减必须自己动手（不用 AI 代劳），这是本规范刻意保留的能力训练环节，见 4.6。

### 4.2 标准版骨架

```text
主题：【需决策】<事项>，影响<业务结果>（<最晚时间> 前确认）

<称呼>，

结论：<问题一句话>。若 <时间> 前仍无法解决，<后果链>。

一、问题
· 事实 / 数据 / 边界

二、后果
· <问题> → <中间环节> → <订单 / 交付 / 成本结果>（尽量量化）

三、关键路径
· 唯一卡点：<人 / 事>（其余条件已具备）
· 最晚决策时间：<日期>（由 <节点> 倒推）
· 若逾期：默认<对外承诺 / 退路>，由 <责任方> 承担结果

四、请求（<时间> 前二选一回复）
A. <方案 A> → <我的动作>
B. <方案 B> → 请明确由 <承担方> 承担<结果>，我同步<商务 / 客户>

<署名>
<日期>
```

### 4.3 简洁版骨架（极简三句法）

四问不删、只压缩，全文 ≤ 200 字：

1. **结论句**（问题 + 后果）：什么问题 + 不解决会怎样，一句写完。
2. **清单**（事项 + 责任人）：每项一行，只写事项与 `@责任人`，不写背景；仅 P0 项补一句"若无法提供，请明确由谁承担"。
3. **末句**（时间 + 兜底）：回复时间 + 交付时间 + 不回复的默认结果。

```text
主题：【需回复】<项目> <N> 项信息未闭环，影响<业务结果>（<时间> 前）

<称呼>，

<N> 项信息仍缺，其中 <唯一卡点> 是唯一卡点。若 <时间> 前拿不到，
<后果链>，<业务结果>。

1. <事项> @<责任人>   ← P0 项补："若无法提供，请明确由谁承担<结果>"
2. <事项> @<责任人>
3. <事项> @<责任人>

第 2–N 项请于 <时间> 前回复时间点，<交付时间> 前交付。

<署名>
<日期>
```

### 4.4 标准版 → 简洁版：删减映射

| 标准版元素 | 简洁版处理 |
| --- | --- |
| 「一、问题 / 二、后果 / 三、关键路径 / 四、请求」标题 | 全部删除，压成结论句 + 清单 |
| 问题段的背景与事实细节 | 删除，只留一句结论 |
| 后果的多个分支 | 只保留一条主链，终点必须是订单 / 交付 |
| 关键路径 3 行 | 压成"唯一卡点"四个字 + `P0` 标签 |
| 请求 A/B 选项 | 压成一句"若无法提供，请明确由谁承担" |
| P1 事项的后果 | 删除，只留时间点 |
| 附件引用、过程说明 | 删除或放附件 |

### 4.5 简洁版范例

```text
主题：【需回复】XX 项目 4 项信息未闭环，影响订单签订（10/17 18:00 前）

Hi 陈工、灿光，

4 项信息仍缺，其中 28 人月分解是唯一卡点。若 10/17 18:00 前拿不到，
人力无法确认 → 排期与报价无法出具 → 商务无法提交方案，订单签订推迟 2 周。

1. 28 人月工作量分解 @陈哲
   按模块的人月分解 + 并行假设；若无法提供，请明确由谁承担订单延期。
2. 校准板（时序、参数）资料及完成时间 @陈工
3. PCIE 卡选型及方案段更新 @灿光
4. 整体解决方案完成时间，请给明确日期 @陈工

第 2–4 项请于 10/17 18:00 前回复时间点，10/20 前交付。

崔永元
2026/10/17
```

### 4.6 训练流程：标准版 → 手工删减 → 核对

这是本规范刻意保留的**能力训练环节**，目的是让删减能力长在自己身上，而不是依赖 AI 代劳。

| 步骤 | 动作 | 要求 |
| --- | --- | --- |
| 1 写全 | 按 4.2 骨架写标准版 | 四问齐全，先写完整，不边写边删 |
| 2 冷却 | 至少隔 30 分钟，或换到手机上看 | 跳出作者视角，切成收件人视角 |
| 3 自己删 | 按 4.4 映射逐条删，不借助 AI | 每删一处，都要能说出"删了不影响决策"的理由 |
| 4 验收 | 用 4.7 六条逐项打勾 | 记录未通过项，不凭感觉判断 |
| 5 对比 | 与 AI 产出的简洁版对照 | 只记差异：我多删了什么、少删了什么 |
| 6 复盘 | 差异点写入待办或周报改进项 | 同类差异出现 2 次，就补进本规范 |

> 建议每周挑 1 封真实邮件做完整演练；连续 4 周后统计"六条一次通过率"，作为能力提升的量化指标。

### 4.7 简洁版验收六条

| # | 验收项 | 判定方法 |
| --- | --- | --- |
| 1 | 篇幅 | 正文 ≤ 200 字（主题、署名不计） |
| 2 | 结论句完整 | 第一段一句话内同时出现"问题"和"后果" |
| 3 | 后果落地 | 后果终点是订单 / 交付 / 客户 / 成本，不是"影响进度" |
| 4 | 只有一条主链 | 全文只出现一个 `P0` 或"唯一卡点"，其余事项不写后果 |
| 5 | 责任到人 | 每个事项都有 `@具体人`，无"相关部门 / 大家" |
| 6 | 时间可考核 | 全文无"尽快 / 稍后 / 及时"，回复与交付时间均具体到日期或时刻 |

**结果处理：**

- 6 条全过 → 可发；
- 过 5 条 → 可发，但必须在邮件中补齐缺失项（通常缺的是时间）；
- ≤ 4 条 → 不发简洁版，直接发标准版。

## 五、标准版范例：软件人力评估无法完成

```text
主题：【需决策】软件人力评估本周无法完成，将影响 X 客户订单引入（10/20 前确认）

彭总，

结论：软件人力评估本周内无法完成。若 10/20 前仍无法确认，X 客户订单引入
将推迟至少 2 周，商务本周无法提交方案。

一、问题
· 评估需 3 名具备 XX 平台量产经验的软件工程师，当前可投入 0 人；
· 缺少 XX 模块工时基线，研发未给出确认口径。

二、后果
· 人力无法评估 → 报价与排期无法出具 → 商务无法在 10/24 前提交方案；
· 客户已定 11/05 评审，延期将影响本季度订单引入；
· 若临时外包赶节点，预计增加成本 XX 万。

三、关键路径
· 唯一卡点：研发对软件人力的确认（其余条件已具备）；
· 最晚决策时间：10/20（倒推 11/05 评审，预留 2 周）；
· 若 10/20 未确认：默认按"延期 2 周"对客户承诺，并由研发侧承担订单
  延期结果。

四、请求（10/20 前二选一回复）
A. 研发确认投入 3 人 → 我按原计划推进；
B. 确认无人力 → 请明确由 XX 承担订单延期结果，我同步商务调整承诺。

崔永元
2026/10/17
```

对照关系：`结论` = 问题 + 后果；`一` = 问题边界；`二` = 后果链；`三` = 关键路径；`四` = 责任与决策请求。

## 六、精简规则

> 两版共用；选版见第四节。

| 规则 | 要求 |
| --- | --- |
| **主题行** | 对象 + 结论/请求 + 时间，独立可读，如「【需决策】A 项目软件人力无法评估，影响订单引入（10/20 前确认）」 |
| **篇幅** | 标准版 300–400 字、简洁版 ≤ 200 字（不含表格与附件），手机端一屏读完结论 |
| **一段一意** | 每段只讲一件事，段首即结论 |
| **能表不段** | 分工、选项对比、多项目进展用表格，不用长段落 |
| **一邮件一主诉求** | 多个诉求必须编号并写明"需要谁回复哪一条" |
| **必须删除** | 多余寒暄（保留一句）、背景复述（放附件）、过程细节、"供参考/辛苦/麻烦"等无信息量词、模糊时间（尽快→具体日期） |
| **引用原文** | 仅保留必要上下文，其余折叠为"原始邮件见下" |

## 七、常用场景骨架

| 场景 | 建议版本 | 骨架 |
| --- | --- | --- |
| **风险升级 / 决策请求** | 标准版（升级或留痕时）；日常催办用简洁版 | 结论 → 问题 → 后果 → 关键路径 → 请求（A/B） |
| **回复确认** | 标准版起草 → 删减为简洁版 | 收到并确认 → 我的结论 → 分工表（事项/负责人/节点）→ 需要对方确认的点 |
| **进度同步** | 标准版起草 → 删减为简洁版 | 结论 → 已完成 / 未完成 → 偏差与原因 → 下一步与时间 |
| **拒绝 / 无法承接** | 标准版 | 结论（不能做）→ 原因（客观约束）→ 替代方案 → 需要的支持与承担方 |

## 八、发出前 Checklist

- [ ] 已选定版本（默认从标准版起草；若删减为简洁版，须过 4.7 六条验收）
- [ ] 主题行能独立看懂结论与时间要求
- [ ] 第一段给出了结论或明确的请求
- [ ] 每个问题都写了后果，且落到订单 / 交付 / 客户 / 成本（简洁版：至少主卡点必须写出后果链）
- [ ] 只保留一个真正的卡点，其余列为已具备条件
- [ ] 有最晚决策时间（由交付节点倒推），没有"尽快"
- [ ] 每个动作都有具体责任人，不是部门
- [ ] 写明了"不做会怎样、谁承担结果"
- [ ] 给了 A/B 选项，而不是只抛问题（标准版）
- [ ] 正文一屏可读完，无重复与客套
- [ ] 需要回复的人已明确 @，并说明回复截止时间

## 九、常见反模式

| 反模式 | 后果 |
| --- | --- |
| 只报现象不报结论 | 领导要自己推演，等于把工作量转嫁上去 |
| 问题平均罗列，没有关键路径 | 收件人不知道该先解决哪个，事情继续拖 |
| 责任写成"相关部门" | 无人认领，最后回到发件人身上 |
| 用"尽快/稍后"代替日期 | 无法考核，也无法触发升级 |
| 抄送一堆人但不明确 @ 谁 | 责任分散，集体沉默 |
| 用背景开头、结论放最后 | 30 秒内读不到重点，邮件被搁置 |
| 一封邮件塞 5 个诉求 | 每个诉求都得不到回应 |
| 情绪化措辞（"已经说过很多次"） | 触发对抗，问题本身被忽略 |

## 十、与其他规范的关系

- **周报模块化格式规范**：周报/月报类邮件正文的模块结构与开头句式。
- **待办梳理规范**：邮件中的待办必须满足"责任人 + 动作 + 时间"，否则不算待办。
- **会议纪要生成规范**：会后邮件直接复用纪要中的结论、待办与责任人，不重新表述。
